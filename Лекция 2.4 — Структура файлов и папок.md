# Лекция 2.4. Структура файлов и папок: логика и автоматизация

**Дисциплина:** Основы работы с информацией.

В сервисной компании два инженера готовят документы по ремонту оборудования. Один сохраняет акты по клиентам, второй раскладывает их по месяцам. Когда заказчик запрашивает подписанный акт, оба находят файл с названием «Акт финал». В одном экземпляре есть подпись, в другом исправлена сумма. Папка полна документов, но команда не знает, какой можно отправить.

Хорошая структура решает три задачи. По адресу и имени можно найти нужный файл. По статусу и версии можно выбрать подходящий экземпляр. По правилам обработки можно повторить работу и проверить, что ничего не потерялось. Эти задачи связаны: красивое дерево папок мало помогает, если никто не знает, где искать подписанный документ.

## 1. Как выбрать основу структуры

**Дерево папок** — способ организации, при котором внутри папки могут быть файлы и другие папки. Внешняя папка задаёт общий контекст. Внутренняя уточняет его. В рабочем примере общая папка называется «Заказы», внутри лежат папки отдельных заказов, а в каждой из них есть документы и фотографии. Такой порядок удобен, когда сотрудник обычно начинает поиск с номера заказа.

![Дерево каталогов Linux: отступы и линии показывают, какая папка находится внутри другой](https://upload.wikimedia.org/wikipedia/commons/1/16/Root_directory_hierarchy_on_Linux_screenshot.webp)

*Рисунок 1 — Дерево папок в Linux. Отступ показывает уровень вложенности, а линии связывают папку с её содержимым.* [Открыть скриншот](https://commons.wikimedia.org/wiki/File:Root_directory_hierarchy_on_Linux_screenshot.webp).

**Путь** — адрес файла или папки. Полный путь начинается с известной точки системы хранения, например с буквы диска в Windows. Относительный путь отсчитывается от выбранной папки. Если папка «Заказы» открыта и сотруднику дали относительный путь к акту, ему достаточно пройти через папку нужного заказа и открыть «Акты». Если он начинает поиск с другого места, тот же относительный путь может указывать совсем не туда.

Для одного набора возможны разные деревья. Представим, что руководитель ежемесячно сверяет все завершённые заказы. Папки по месяцам облегчат его задачу. Инженер чаще ищет всю историю одного заказа, даже если тот начался в ноябре и закончился в декабре. Для него удобнее хранить всё по номеру заказа, а месяц окончания указать в каталоге. Большинство компаний не обязаны выбирать структуру один раз на все случаи. Папки обслуживают основной способ поиска. Дополнительные признаки можно вынести в таблицу или каталог.

| Как обычно ищут материал | Удобная основа папок | Что добавить в каталог |
| --- | --- | --- |
| По номеру заказа | Заказ, затем вид материала | Дата завершения и ответственный |
| По периоду отчёта | Год, затем месяц | Номер заказа и статус |
| По виду документа | Акты, счета, инструкции | Проект, редакция и права доступа |

Если один акт нужен в отчёте за месяц и в истории заказа, кажется естественным скопировать его в обе папки. Через неделю исправление появится только в одном месте, и возникнут две версии без ясной связи. При общей работе полезно заранее определить, где лежит основной экземпляр. Второй путь к нему можно дать через ссылку или запись в каталоге. Если нужна отдельная копия для отчёта, зафиксируйте, на какую дату она сделана и кто её сформировал.

Удобство дерева можно проверить простым способом. Дайте коллеге номер заказа и попросите найти подписанный акт. Затем попросите собрать акты за месяц. Если по номеру файл находится легко, а для месячного отчёта приходится открывать двадцать папок, добавьте поле «Дата подписания» в каталог. Переносить весь архив ради второго сценария обычно излишне.

## 2. Что включать в имя файла

**Правило именования** задаёт, какие части должны присутствовать в имени и в каком порядке. В учебном примере команда использует номер заказа, тип документа и номер версии. Файл «R042-акт-v02.pdf» можно отличить от акта по другому заказу даже в письме или в папке «Загрузки». Номер версии остаётся удобным для сортировки, если для однотипных файлов заранее договориться об одинаковой длине номера.

Дата в имени помогает, когда документ привязан к конкретному событию. Например, «2026-11-19-отчёт-склад.pdf» удобно расположить рядом с другими ежедневными отчётами. Формат «год, месяц, день» позволяет сортировать даты как текст, если месяц и день записаны двумя цифрами. Но сначала нужно уточнить, что означает дата. Дата съёмки, дата создания копии и дата подписания — разные события. Для акта, который ищут как подписанный, в имени или карточке лучше указывать именно дату подписания.

Часть сведений можно оставить в папке. Если путь уже содержит номер заказа, его повторение во всех именах удлиняет список. Если файлы регулярно отправляют отдельно, номер в имени помогает сохранить контекст. Справочник Национального архива США по организации цифровых материалов предлагает при выборе имени учитывать, останется ли файл понятным вне исходной структуры папок. Этот вопрос полезен и для личных файлов. Например, «квитанция.pdf» внутри папки «Интернет, ноябрь» понятна владельцу. При пересылке понятнее имя «2026-11-квитанция-интернет.pdf». [Рекомендации Национального архива США](https://www.archives.gov/files/preservation/formats/pdf/naming-and-organizing-files.pdf).

**Расширение** — часть имени после последней точки, например `.pdf` или `.jpg`. Оно помогает системе выбрать программу для открытия файла. Замена `.jpg` на `.png` не преобразует изображение. Для преобразования нужно открыть файл и сохранить его в новом формате средствами программы. Этот эффект важно понимать при массовом переименовании: если содержимое должно сохраниться, расширение обычно оставляют прежним.

Для переносимого набора проверьте имена на тех системах, где будут работать с файлами. Одно хранилище может различать прописные и строчные буквы, другое — воспринимать два таких имени как одинаковые. Например, «Акт.pdf» и «акт.pdf» не стоит считать отличающимися только регистром, если документы копируют между разными устройствами. Формат имени должен оставаться удобным людям и выдерживать реальные переносы.

## 3. Как отличать версию, статус и копию

**Версия** — состояние материала на определённом этапе работы. Версии отличаются содержимым. **Статус** показывает назначение этого состояния: черновик, на согласовании, утверждено или архив. **Копия** — экземпляр того же содержимого в другом месте. Эти сведения отвечают на разные вопросы. Если последняя версия пока не утверждена, отправлять заказчику всё равно нужно более ранний подписанный акт.

Допустим, команда подготовила версию 3 акта и ждёт подпись. Версия 2 уже подписана. В каталоге версию 3 отмечают как «На согласовании», а версию 2 как «Утверждено». Когда подпишут третью версию, ответственный обновит оба статуса: новая станет действующей, а предыдущая перейдёт в архив, если этого требуют правила хранения. Тогда коллега сможет найти и текущий экземпляр, и историю согласования. Простое слово «финал» не передаёт эту последовательность.

Статус можно хранить в названии файла, в карточке или в системе согласования. За значение должен отвечать один источник. Если название содержит «утверждено», а в журнале указано «отозвано», сотруднику нужно знать, что проверять первым. Для отправки внешнему получателю пригодится имя, понятное вне хранилища. Внутри команды надёжнее использовать поле статуса, которое обновляет ответственный.

**Журнал версий** сохраняет предыдущие состояния файла. В OneDrive и SharePoint через него можно открыть или восстановить более ранний вариант, если функция доступна. Например, сотрудник случайно заменил рабочую таблицу пустой заготовкой. Если история сохранилась, можно вернуть предыдущее состояние. Журнал отвечает на вопрос «каким был файл раньше». Для вопроса «какая редакция подписана» всё равно нужна отметка о согласовании. [Как восстановить предыдущую версию в OneDrive](https://support.microsoft.com/ru-ru/onedrive/restore-a-previous-version-of-a-file-stored-in-onedrive).

У восстановления есть и обратная сторона. Если вернуть старую версию после согласования новой, её содержимое снова станет текущим. Перед восстановлением полезно сверить дату и описание изменения, проверить доступ к документу и сообщить ответственному по обычному рабочему процессу. После восстановления откройте файл и убедитесь, что вернулась нужная информация. История версий помогает восстановить содержимое, а резервная копия нужна ещё и тогда, когда основное хранилище или сама история недоступны.

## 4. Как автоматизировать изменения

**Автоматизация** передаёт программе повторяющиеся действия по заданным правилам. Например, в папку каждый день поступают фотографии с именами камеры. Оператор проверяет номер заказа и добавляет его к имени копии для отчёта. При трёх фотографиях работу можно выполнить вручную. При трёхстах есть смысл составить таблицу соответствий и поручить программе преобразовать имена по этой таблице.

Первый шаг — описать правило словами. Допустим, фотографии заказа R042 нужно назвать по номеру заказа и порядку съёмки. Номер берём из карточки заказа, порядок — из подтверждённого списка оператора. Файлы с неизвестным заказом откладываем на уточнение. Если порядок съёмки неизвестен, использовать произвольную сортировку по имени рискованно. Автоматизация повторит этот выбор для всей папки.

Второй шаг — составить **план преобразования**. В таблице для каждого объекта указаны прежний путь, новое имя и причина изменения. Когда два разных файла получают одинаковый адрес назначения, возникает **конфликт имён**. Например, для одного заказа дважды выбрали номер фото 01. Оператор должен уточнить порядок или проверить, являются ли файлы копиями. Перезапись первого файла вторым уничтожит информацию о различии.

| Исходный файл | Запланированное имя | Что проверить |
| --- | --- | --- |
| IMG_1032.jpg | R042-фото-01.jpg | Номер заказа подтверждён |
| IMG_1033.jpg | R042-фото-02.jpg | Имя ещё свободно |
| IMG_1034.jpg | Оставить без изменения | Заказ неизвестен |

Третий шаг — посмотреть, что программа собирается сделать. **Предварительный просмотр** выводит действия без изменения файлов. В PowerShell команда `Rename-Item` переименовывает элемент, а параметр `-WhatIf` показывает предполагаемое действие. Параметр `-LiteralPath` позволяет передать путь буквально. Например, квадратные скобки в имени файла сохранят свой смысл обычных символов. Пример рассчитан на отдельную учебную копию одного файла. [Документация Microsoft о Rename-Item](https://learn.microsoft.com/ru-ru/powershell/module/microsoft.powershell.management/rename-item?view=powershell-7.5).

```powershell
Rename-Item -LiteralPath '.\IMG_1032.jpg' -NewName 'R042-фото-01.jpg' -WhatIf
```

Предварительный просмотр не знает, правильный ли номер заказа ввёл человек. Перед обработкой проверьте саму папку, число выбранных файлов, расширения и отсутствие конфликтов. Затем выполните пробную обработку нескольких копий и проверьте, как они открываются. Отдельно продумайте повторный запуск. Если правило добавляет префикс без проверки, повторная обработка даст имя «R042-R042-фото-01.jpg». Можно исключать уже обработанные файлы или работать по списку исходных путей, который явно отделён от списка результатов.

После выполнения полезен **журнал изменений**: список выполненных операций и ошибок. Если обработка остановилась на двадцатом файле, журнал покажет, какие девятнадцать уже переименованы. Сотрудник сможет исправить причину и продолжить с оставшихся. По таблице соответствий можно вернуть прежние имена, когда исходный и новый адреса известны и эти имена всё ещё свободны. Перед крупной операцией лучше иметь отдельно сохранённую копию входного набора.

## 5. Что проверять при переносе и совместной работе

Перенос папки меняет адреса файлов. Если внутри неё лежит отчёт со ссылками на соседние фотографии, относительные ссылки могут продолжить работать после переноса всей папки. Полные ссылки на старый диск могут сломаться. Например, документ ссылается на файл внутри «Заказы», а снимки переехали в облако. На компьютере автора всё ещё есть старый диск, поэтому он не замечает поломки. Коллега открывает отчёт и видит только пустые места. Результат переноса проверяют там, где им действительно будут пользоваться.

Проверка касается и доступа. Если к общей папке подключили подрядчика, вложенная папка может получить те же права, что и внешняя. В ней могут оказаться внутренние акты или фотографии с личными сведениями. Перед переносом ответственный должен решить, какие файлы нужны подрядчику, куда они попадут и кто сможет открыть ссылку. Название папки «Внутреннее» помогает людям ориентироваться, а доступ определяют настройки хранилища.

Новый порядок полезно описать в короткой инструкции вместе с примерами. Укажите основу папок, образец имени, место для действующей версии и действие при конфликте. Затем пройдите обычный сценарий: найдите подписанный акт, откройте связанную фотографию и проверьте, что у внешнего получателя доступны только предназначенные ему материалы. Так можно проверить, переживает ли структура повседневную работу, перенос и обновление.

Если с изменениями работают несколько человек, договоритесь о моменте переноса. Например, сотрудник исправляет акт, пока коллега переносит папку. Если правка сохранилась в старом месте после копирования, новая папка отстанет от исходника. На время переноса можно согласовать короткую остановку правок либо после копирования выполнить вторую сверку изменённых файлов. Решение зависит от того, насколько часто документы обновляются и можно ли временно закрыть запись. Итог переноса полезно проверить по числу файлов, контрольным документам и рабочим ссылкам.

Наконец, определите, что делать с прежним расположением. Ссылка на новое место и дата перехода помогут сотрудникам сменить привычку. Если оставить старую папку рабочей, часть команды продолжит писать в неё. Если сразу убрать её, можно потерять единственную доступную копию или источник для сравнения. Правила хранения и доступ к прежней версии стоит согласовать заранее.

### Как понять, что порядок прижился

Через несколько недель после перехода руководитель видит, что в папке «Входящие» снова накопились сотни файлов. Часть сотрудников получает по пять документов за день, а часть — по пятьдесят. Всем приходится вручную открывать вложение, искать номер заказа и менять имя. Проблема возникает на входе. Сотрудникам нужно получать номер заказа вместе с документом либо отмечать неизвестный номер и передавать такой файл на уточнение. Перестановка уже накопившихся папок временно улучшит вид, а новый поток быстро вернёт прежний беспорядок.

Для папки «Входящие» можно установить простое правило. Ответственный проверяет, с каким заказом связан материал, и переносит его в нужное место. Если связи пока нет, запись остаётся на уточнении с датой поступления. Благодаря дате можно заметить файлы, которые лежат без решения дольше обычного. Когда номер уточнили, файл перемещают и обновляют его адрес в каталоге. Процесс становится понятен даже сотруднику, который впервые замещает коллегу.

Проверьте новый порядок по результату. Если до изменения поиск акта требовал спросить двух коллег, а после изменения ответ находится по номеру заказа, структура решает реальную задачу. Если акт находится быстро, но приходится угадывать, какая редакция подписана, следующим улучшением будет статус и правило его обновления. Для проверки полезно взять несколько случаев: открытый заказ, завершённый заказ, файл без номера и заказ с двумя редакциями. Такое сравнение показывает, где новое правило работает, а где требуется дополнительное решение.

У папок и имён есть пределы. Когда один документ нужно искать по нескольким полям и доступ зависит от роли, полезно хранить эти поля в каталоге. В дереве достаточно сохранить понятный адрес. Дополнительную работу по отбору выполнит поиск по признакам, рассмотренный в предыдущей лекции.

## Заключение

Порядок в файлах начинается со сценария поиска. Папки дают контекст, имя помогает узнать материал, каталог хранит признаки, а статус подсказывает, какую версию использовать. Автоматизация полезна после того, как эти правила понятны человеку. Она безопаснее, когда есть план изменений, пробный запуск на копиях и способ проверить результат.
